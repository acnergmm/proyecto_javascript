Formularios: acá se ve para qué sirve JavaScript

Un formulario es la razón por la que existe casi todo el JavaScript del mundo. Registrarse, iniciar sesión, comprar, buscar, comentar: todo es un formulario. Y sin JavaScript, todos funcionan mal.

Formulario 1 — sin JavaScript (el problema)

Atención: este formulario se manda de verdad. Completalo y apretá Enviar: la página se recarga, se pierde todo lo que escribiste, y los datos aparecen a la vista de todos en la barra de direcciones. Después volvé con la flecha atrás del navegador.

Los tres problemas, en orden de gravedad:

  1. La página se recarga. Se pierde todo el estado: lo escrito, la posición del scroll, el carrito.
  2. El error llega tarde. Si el email estaba mal escrito, el usuario se enteró después de mandarlo, y tiene que escribir todo de nuevo.
  3. No hay control. Podemos mandar el campo vacío, una edad negativa o un email que no es un email.

Formulario 2 — con JavaScript (la solución)

Escuchamos el evento submit y le pedimos al navegador que no haga lo que iba a hacer. Esa es la línea más importante de todo el bloque: 

formulario.addEventListener("submit", (evento) => {
    evento.preventDefault();   // <-- no recargues la pagina, dejame manejarlo a mi
    // desde aca los datos son nuestros
});

El evento submit va en el <form>, no en el botón. Así se dispara tanto con el click como cuando el usuario aprieta Enter dentro de un campo.

El atajo: FormData

Leer campo por campo está bien para entender qué pasa. Pero cuando el formulario tiene quince campos, el navegador nos da una herramienta que los lee todos de una: 

const datos = new FormData(formulario);
const objeto = Object.fromEntries(datos);
// { nombre: "Ana Pérez", email: "ana@ejemplo.com", edad: "28", ... }

Usa el atributo name de cada campo, no el id. Por eso los campos del formulario de arriba tienen los dos.

¿Y la validación que ya trae el HTML?

El HTML sabe validar solo: required, type="email", minlength, min y max. Es gratis y hay que usarla siempre.

Pero no alcanza, por tres razones:

  • Los mensajes no se pueden redactar ni traducir bien, y cambian según el navegador.
  • No puede validar reglas nuestras: que dos contraseñas coincidan, que el usuario no exista ya, que el DNI tenga el formato correcto.
  • Se puede desactivar desde las herramientas del navegador en diez segundos, así que el servidor siempre tiene que validar de nuevo. La validación en el navegador es para el usuario, no para la seguridad.

La combinación correcta: required en el HTML para lo básico, JavaScript para las reglas propias y los mensajes lindos, y el servidor validando todo otra vez.
